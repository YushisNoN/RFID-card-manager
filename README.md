# RFID Card Manager

Серверная часть системы **RFID Card Manager** — проекта для учёта выдачи и возврата плат с помощью RFID-карт. Контроллер на ESP32 считывает UID карты и отправляет его на HTTP-сервер. Сервер обрабатывает событие, сохраняет текущее состояние карты и историю операций в PostgreSQL, а веб-интерфейс получает статистику и историю через REST API.

> Проект находится в разработке. Описание ниже соответствует текущей реализации сервера и базы данных.

## Возможности

- Приём UID RFID-карты от контроллера через HTTP.
- Преобразование UID в шестнадцатеричное представление для хранения в базе данных.
- Переключение состояния карты между выдачей и возвратом.
- Сохранение каждого события в журнале операций.
- Получение общей статистики по картам и операциям.
- Получение последних событий из истории.
- Раздача статических файлов веб-интерфейса самим Zig-сервером.
- Подключение к PostgreSQL через пул соединений.
- Сборка и развёртывание серверной части с помощью Docker Compose.

## Архитектура

Система состоит из трёх основных частей:

1. **Контроллер ESP32** считывает UID RFID-карты и отправляет его серверу.
2. **Zig HTTP Server** принимает запрос, проверяет входные данные, выполняет операцию в базе данных и возвращает JSON-ответ. Кроме API сервер раздаёт статические файлы веб-интерфейса.
3. **PostgreSQL** хранит текущее состояние карт и историю операций.

Веб-интерфейс обращается к API сервера и отображает статистику и историю.

```mermaid
flowchart LR
    RFID[RFID-карта] --> ESP[ESP32 + RFID-считыватель]
    ESP -->|HTTP POST /api/checkUID| SERVER[Zig HTTP Server]
    WEB[Веб-интерфейс] -->|HTTP GET| SERVER
    SERVER -->|SQL через connection pool| DB[(PostgreSQL)]
    SERVER -->|JSON / статические файлы| WEB
```

Все компоненты могут взаимодействовать внутри одной Docker-сети. В текущей конфигурации сервер слушает порт `8080` внутри контейнера, а Docker публикует его на порт `80` хоста.

## Как работает учёт карт

Для каждой карты в таблице `card_issuances` хранится признак `issued`:

- `TRUE` — карта отмечена как выданная;
- `FALSE` — карта отмечена как возвращённая или ещё не выданная.

При получении UID сервер вызывает `Database.checkAndProcessCard`. Операция выполняется одним SQL-запросом с CTE:

1. Если UID встретился впервые, создаётся запись с `issued = TRUE` и временем выдачи `issued_at = NOW()`.
2. Если запись уже существует и `issued = FALSE`, состояние меняется на `TRUE`, а `issued_at` устанавливается в текущее время.
3. Если запись существует и `issued = TRUE`, состояние меняется на `FALSE`, а `issued_at` сбрасывается в `NULL`.
4. Одновременно в `rfid_events` добавляется событие `board_taken` или `board_returned`.

Таким образом, повторное считывание одной карты переключает её состояние между выдачей и возвратом.

**Важно:** в текущей реализации `CardResult.allowed` возвращается как `true` и для выдачи, и для возврата. Это поле пока не реализует проверку прав доступа или белый список разрешённых карт.

## HTTP API

Сервер предоставляет следующие маршруты.

### `POST /api/checkUID`

Обрабатывает UID RFID-карты. Ожидает JSON с количеством значимых байтов и массивом байтов UID.

**Пример запроса:**

```http
POST /api/checkUID HTTP/1.1
Content-Type: application/json

{
  "size": 4,
  "bytes": [4, 123, 22, 89]
}
```

Поля запроса:

| Поле | Тип | Описание |
|---|---|---|
| `size` | `usize` | Количество байтов UID, которые нужно обработать. Должно быть больше нуля и не превышать длину `bytes`. |
| `bytes` | массив чисел | Байты UID RFID-карты. |

Сервер использует первые `size` элементов массива `bytes` и преобразует их в шестнадцатеричную строку.

**Пример успешного ответа при выдаче:**

```json
{
  "allowed": true,
  "status": "board_taken",
  "message": "Плата успешно взята"
}
```

**Пример успешного ответа при возврате:**

```json
{
  "allowed": true,
  "status": "board_returned",
  "message": "Плата успешно сдана"
}
```

В текущей реализации при `allowed: true` сервер отвечает HTTP `200`. Для результата с `allowed: false` предусмотрен HTTP `409`, однако используемая сейчас логика базы данных всегда возвращает `allowed: true`.

### `GET /api/stats`

Возвращает агрегированную статистику:

| Поле | Описание |
|---|---|
| `total_cards` | Общее количество записей о картах. |
| `taken_cards` | Количество карт с `issued = TRUE`. |
| `available_cards` | Количество карт с `issued = FALSE`. |
| `total_events` | Общее количество событий в журнале. |
| `total_takes` | Количество событий `board_taken`. |
| `total_returns` | Количество событий `board_returned`. |
| `events_today` | Количество событий с начала текущего дня по времени PostgreSQL. |
| `avg_duration_ms` | Среднее время между выдачей и следующим возвратом одной карты, в миллисекундах. |

Средняя продолжительность рассчитывается по последовательным событиям одной карты. В расчёт попадают пары `board_taken` → `board_returned`.

### `GET /api/history`

Возвращает историю последних событий. Запрос к базе данных выбирает не более 50 записей, отсортированных по `created_at` от новых к старым.

Поля одной записи истории:

| Поле | Описание |
|---|---|
| `id` | Идентификатор события. |
| `uid` | UID карты в шестнадцатеричном представлении. |
| `event_type` | Тип события: `board_taken` или `board_returned`. |
| `timestamp` | Временная метка события в миллисекундах Unix time. |

### Статические файлы

GET-запросы, не относящиеся к `/api/`, обрабатываются как запросы статических файлов из каталога `public`. Сервер проверяет путь на наличие `..`, чтобы не допускать выхода за пределы каталога статических файлов.

Для фронтенда рекомендуется использовать относительные адреса API:

```javascript
fetch('/api/stats');
fetch('/api/history');
```

## База данных

При инициализации `Database.init` создаёт пул PostgreSQL с размером до пяти соединений и проверяет наличие необходимых таблиц и индексов.

### Таблица `card_issuances`

Хранит текущее состояние каждой карты.

| Поле | Тип PostgreSQL | Назначение |
|---|---|---|
| `uid` | `VARCHAR(64)` | UID карты, первичный ключ. |
| `issued` | `BOOLEAN` | Текущее состояние карты; по умолчанию `FALSE`. |
| `issued_at` | `TIMESTAMPTZ` | Время последней выдачи; при возврате сбрасывается в `NULL`. |

### Таблица `rfid_events`

Хранит историю операций. Записи не заменяют друг друга: каждое событие добавляется отдельно.

| Поле | Тип PostgreSQL | Назначение |
|---|---|---|
| `id` | `BIGSERIAL` | Первичный ключ события. |
| `uid` | `VARCHAR(64)` | UID карты. |
| `event_type` | `VARCHAR(32)` | Тип события. |
| `created_at` | `TIMESTAMPTZ` | Время создания события; по умолчанию `NOW()`. |

Создаются индексы:

- `idx_rfid_events_created` по `created_at`;
- `idx_rfid_events_uid` по `uid`.

## Требования

Для сборки и запуска вне Docker необходимы:

- Zig **0.17.1**;
- PostgreSQL;
- доступная зависимость `pg`, объявленная в `build.zig.zon`;
- переменная окружения `DATABASE_URL`.

Для контейнерного запуска дополнительно нужны Docker Engine и Docker Compose.

## Локальная сборка и запуск

### 1. Клонирование репозитория

```bash
git clone git@github.com:YushisNoN/RFID-card-manager.git
cd ZigServer
```

Чтобы клонировать конкретную ветку:

```bash
git clone --branch server --single-branch git@github.com:YushisNoN/RFID-card-manager.git
cd ZigServer
```

### 2. Настройка подключения к PostgreSQL

Предварительно необходимо создать базу данных и пользователя PostgreSQL. Затем задать переменную окружения `DATABASE_URL`.

**PowerShell:**

```powershell
$env:DATABASE_URL = "postgresql://USER:PASSWORD@localhost:5432/DATABASE_NAME"
```

**Linux / macOS:**

```bash
export DATABASE_URL="postgresql://USER:PASSWORD@localhost:5432/DATABASE_NAME"
```

### 3. Сборка

```bash
zig build
```

### 4. Запуск

```bash
zig build run
```

Сервер запускается на порту `8080` и слушает входящие подключения на всех сетевых интерфейсах (`0.0.0.0`). При старте он подключается к PostgreSQL. Если `DATABASE_URL` отсутствует или подключение к базе данных не удалось, запуск завершается с ошибкой.

## Запуск в Docker

В текущей конфигурации Zig-сервер запускается в отдельном контейнере. PostgreSQL может работать в другом контейнере, подключённом к той же Docker-сети.

Пример Compose-конфигурации сервера:

```yaml
services:
  zigserver:
    build:
      context: .
      dockerfile: Dockerfile
    container_name: rfid_server
    restart: unless-stopped
    env_file:
      - .env
    ports:
      - "80:8080"
    networks:
      - rfid_network

networks:
  rfid_network:
    external: true
```

### 1. Создание Docker-сети

Если сеть ещё не создана:

```bash
docker network create rfid_network
```

Контейнер PostgreSQL также должен быть подключён к `rfid_network` и доступен серверу под сетевым именем `postgres` (например, через network alias).

### 2. Создание `.env`

В корне проекта должен лежать файл `.env`:

```dotenv
DATABASE_URL=postgresql://USER:PASSWORD@postgres:5432/DATABASE_NAME
```

Здесь `postgres` — имя или сетевой alias контейнера PostgreSQL, а не `localhost`.

### 3. Сборка и запуск контейнера

```bash
docker compose up -d --build
```

Проверить состояние контейнера:

```bash
docker compose ps
```

Посмотреть логи сервера:

```bash
docker compose logs -f zigserver
```

После запуска веб-интерфейс и API доступны через HTTP на порту `80` хоста:

```text
http://<SERVER_IP>/
http://<SERVER_IP>/api/stats
http://<SERVER_IP>/api/history
```

При обновлении исходников:

```bash
git pull
docker compose up -d --build
```

> Эта Compose-конфигурация подключает сервер к уже существующей внешней сети. Она не создаёт контейнер PostgreSQL автоматически: база данных должна быть запущена отдельно и доступна в этой сети.

## Генерация документации Zig

В проекте предусмотрены документационные комментарии Zig:

- `//!` — описание файла или модуля;
- `///` — описание публичных объявлений, функций, структур и полей.

Сгенерировать HTML-документацию:

```bash

```


## Текущие ограничения и безопасность

- **Нет полноценной аутентификации API.** В показанной реализации HTTP-маршруты не защищены пользовательской авторизацией. Не следует без дополнительной защиты выставлять сервер в недоверенную сеть.
- **Нет HTTPS внутри приведённой конфигурации.** Публикация `80:8080` означает обычный HTTP. Для передачи данных через недоверенные сети необходимо предусмотреть HTTPS на уровне инфраструктуры.
- **`allowed` пока не означает проверку разрешений.** Метод обработки карты возвращает `allowed = true` для обеих операций. Это результат текущего алгоритма переключения состояния, а не механизм контроля доступа.
- **Размер тела запроса ограничен.** Сервер принимает тело запроса размером до 4096 байт.
- **История ограничена 50 событиями.** API не предоставляет пагинацию в текущей реализации.
- **Список MIME-типов статических файлов ограничен.** Для HTML, CSS и JavaScript используются соответствующие типы; остальные файлы могут отдаваться как `application/octet-stream`.
- **CORS preflight не реализован.** Для текущей схемы с фронтендом и API на одном origin это обычно не требуется. При размещении фронтенда на другом origin понадобится отдельно настроить CORS.

## Решение частых проблем

### Сервер не подключается к PostgreSQL в Docker

Проверьте, что контейнер PostgreSQL запущен, подключён к сети `rfid_network`, а его сетевое имя или alias совпадает с хостом в `DATABASE_URL`. При обращении из контейнера Zig значение `localhost` указывает на сам контейнер Zig, а не на контейнер базы данных.

### Веб-интерфейс не получает данные API

Проверьте запросы во вкладке Network браузера. При размещении фронтенда и API на одном сервере используйте относительные пути (`/api/stats`, `/api/history`, `/api/checkUID`), а не `http://127.0.0.1:8080`.

### Документация Zig открывается пустой или не загружает WASM

Не открывайте `zig-out/docs/index.html` через `file://`. Перейдите в каталог `zig-out/docs`, запустите `python -m http.server 8000` и откройте `http://localhost:8000/`.
